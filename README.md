# linktool

把一棵树里的重复文件和链接收拢成一个源加若干链接，再把它们按记录重建回来。主要用在 Windows 与 Android/Termux 之间搬运目录：先在本机把重复项移走，让复制工具只搬唯一的内容，到了目标机再按记录把链接补回来。

## 运行

需要 Python 3.14 以上。

仓库自带 `uv` 环境：

```
uv sync
uv run linktool --help
```

用系统 Python 时把 `src` 加进导入路径，`xxhash` 需要预先装好：

```
PYTHONPATH=src python -m linktool --help
```

`python -m pip install .` 把 `linktool` 装进 `PATH`，构建时要联网下载 hatchling。

## 命令

| 命令 | 作用 |
| --- | --- |
| `remove` | 每组重复内容只留一个源，其余路径删除 |
| `stage` | 与 `remove` 相同，但把其余路径移进暂存区 |
| `rebuild` | 按记录把被移走的路径重建为硬链接、符号链接或副本 |
| `restore` | 把暂存区里的条目移回原位 |
| `fix` | 修复因源被移动而失效的符号链接 |
| `status` | 报出状态区或暂存区里还剩什么 |

所有命令都先算出计划再执行：扫描或读记录，得出每条路径的去向；无法自主决定的项写进 `<state>/.linktool/` 下的一对文件并返回退出码 3，填好答卷后重跑同一条命令才真正执行。执行成功后这一轮的两个文件一起删掉，下一轮重新生成。

`plan-<命令>.json` 只存工具要读的三项：`version`、`command`，以及记着生成这次计划的全部设置的 `args`。给人看的内容全在 `plan-<命令>.toml`：先是 `decisions` 段，逐组列出由规则定下的源、依据与将要移走的路径；再是这一轮走到的题目，每题一段注释说明题面与可填项，末行 `'<id>' = ''` 等待填写。答案只写在答卷里。

重跑时逐项比对 `args`，命令或任何一项设置不同就拒绝；想沿用已填的答案，把 `args` 段改成这次的参数再重跑。已经答过的题在新一轮里仍列在答卷上并标着「已采纳」，改动那一行就是改答案。只有 `--state` 与它旁边这对计划文件被删掉时，答案才会清空。

`remove` 与 `stage` 另有一道总确认：整份计划汇成一题，答 yes 之前不会动任何一条待处理的路径，所以这两个命令通常要跑两轮。

## 跨机流程

源机：

```
linktool stage --scan D:/tree --staging H:/stage
```

`--state` 与 `--base` 缺省时都取这唯一的扫描路径，记录落在 `D:/tree/.linktool/`。剩下的每一份内容都只剩一条路径，硬链接和符号链接都已移走，复制工具没有可展开的链接。

复制工具要把整棵树连同 `.linktool/` 一起搬走，目标机的 `rebuild` 全靠它。

源机随后还原暂存区，这一步与目标机的重建互不影响：

```
linktool restore --state D:/tree
```

目标机按记录重建：

```
linktool rebuild --state /storage/emulated/0/tree
```

同一台机器上去重只需要 `remove` 加 `rebuild`。

## 状态与记录

`<state>/.linktool/state.json` 记录每一组的源、每个被移走路径的原形态、修改时间、创建时间（只有 Windows 读得到）和重建状态，以及这份记录用的基准目录和它交给过的暂存区；`state.jsonl` 是逐条进度的追加日志，收尾时并回 `state.json`，崩溃后下次启动先合并一次。两份文件都随树复制，目标机不需要源机在位。

`state.json` 里同时记着写入时的 `state` 与 `base`。记录的路径以 `base` 为基准；写入时 `base` 等于 `state` 的记录，读到它时按本次给出的 `state` 解析，因此整棵树搬到哪里都成立。写入时把基准提到了上级（`--base` 高于 `--state`）的记录，本次推导出的基准与记录里的不同时出一道 `base-` 题，问路径按哪个基准解析，默认取记录里的那个；写入类命令选本次的值时把这个字段改成新值。作为基准的目录必须存在，否则报错并同时给出记录里的值与本次的值，且在建立任何目录之前停下。

暂存区自己拥有 `<staging>/.linktool/staging.json`，记录每个条目的原位置和它在暂存区里的位置，并写明自己属于哪份记录。暂存区不能位于任何扫描路径之内，否则复制工具会把它的内容一并搬走；也不能就是状态目录。`restore` 只认 `--state`，从 `state.json` 里读出这份记录交给过哪些暂存区并逐个处理。清单不在原处时 `restore` 列出这些路径并失败，`status` 对那个区报「暂存区缺失」并继续报其余的。一个暂存区只服务一份记录，用另一份记录访问它会被拒绝。暂存区与文件同卷时，移入与还原只做改名：inode 与两个时间原样跟过去，原本与它共享 inode 的路径仍读同一份数据。跨卷时才复制一份再删原件。

`status` 报出记录与各暂存区各自还剩多少条。给暂存区时，首行写出它所属的状态区，随后列出待还原的条目，其中清单上有而磁盘上找不到的那几条在后面标注。清空与否由用户决定，代价分别是：

- 还有待重建成员时删掉 `state.json`，`rebuild` 失去依据，`fix` 也失去按内容找候选的依据。
- 还有待还原条目时删掉 `staging.json`，这些条目失去原位置，`restore` 再也找不到它们。
- 计划文件随时可删，代价是下次重跑要重新回答。

路径在 `state.json` 里记成相对基准目录的形式并且用 `/` 分隔，同一份记录在 Windows 的 `D:/tree` 和 Android 的 `/storage/emulated/0/tree` 上都能解析。基准目录之外的路径用 `../` 跨出基准，因此把整棵树连同它的上级一起拷到别处后，`rebuild` 把链接建在新位置的对应路径上。落在另一个卷上的路径没有相对形式，记成绝对路径。

## 判断重复

### 内容的判定

扫描只认普通文件和链接，目录只用来往下走。名为 `.linktool` 的目录整棵跳过，所以记录不会把自己扫进结果。指向不存在目标的符号链接不成组，扫描时逐个报一行警告。

先按大小分组，再对 1 MiB 以上的文件取首尾各 4 KiB 做快速哈希，最后全量 `xxhash.xxh3_128`。最终身份是「大小 + 全量哈希」。符号链接按它解析出的文件参与内容分组，目录链接按解析出的目录分组。链接本身只算它自己这一条路径，内容不继承自目标目录里的其他文件，所以同一目录下的两个链接按两个成员处理。

### 源的选择

组里的源按两条规则定：组内符号链接解析出的 realpath 唯一时用那个 realpath；否则若偏好目录下恰好一个成员就用它。两条规则都成立却指向不同文件时整组进问题文件。命中偏好目录的组成员是链接时，链接新源指向它的 realpath；同目录下的多个硬链接按一个源对象计数。

两条规则都不成立时由 `--pick` 决定：`ask` 逐组提问，`first` 按路径排序取最前。`first` 选出的源同样进 `decisions` 段，与其他源一并确认。

## 重建形态

原先是什么形态，重建出来还是什么形态：原先是文件的按「硬链接 → 符号链接 → 副本」降级；原先是链接的建成链接，只有指向文件的链接在目标卷不支持符号链接时落成同内容的副本。

硬链接要求源与目标同卷。符号链接与硬链接的支持情况由在目标目录里创建一次探针并按卷缓存来判断。要回退副本时，所有副本的预估总大小先进问题文件，用户确认后才复制。

指向目录的链接没有副本形态，副本意味着把整个目录复制一份。目标卷不支持符号链接时，这类链接连同路径写进问题文件，确认后跳过；暂存与还原时目标卷放不住的链接也同样跳过，因为这两处要保住原形态，否则还原后链接变成文件。跳过后的结果是重建时保持待重建，还原时留在暂存区，暂存时留在原处。

## 问题与退出码

问题分三类。`confirm` 填 `yes` 或 `no`。`choice` 填候选序号、候选值或 `skip`。`fill` 填候选序号、本机路径或 `skip`。每道题的注释列出该题接受的全部写法。值用单引号括起，反斜杠原样保留，所以 Windows 路径可以直接抄进去；值里有单引号时改用双引号并把反斜杠写成 `\\`。

填了无效值时，工具保留填过的原文，在下一轮的答卷上于这道题上方标出原因，并停在这一轮。空着不填的题同样让命令停在等待答案的那一轮。

问题 id 的前缀说明这道题在问什么：

| 前缀 | 何时出现 | 可填 |
| --- | --- | --- |
| `scan-` | 扫描路径在基准目录之外 | `yes` / `no` |
| `base-` | 记录里的基准与本次推导出的不同 | `recorded` / `given` 或序号 |
| `source-` | 两条选源规则指向不同文件，或都不成立且 `--pick` 为 `ask` | 候选序号、候选值、`skip` |
| `outside-` | 选定的源在基准目录之外 | `yes` / `no` |
| `unavailable-` | 目标卷不支持符号链接，而这个链接没有副本形态 | `yes` / `no` |
| `copy-` | 有成员只能重建为副本 | `yes` / `no` |
| `clash-` | 重建或还原的目标位置已被占用且内容不同 | `replace` / `skip` 或序号 |
| `missing-` | 记录里的源已不存在 | 本机路径或 `skip` |
| `fix-` | `fix` 找到多个候选源，或一个也没有 | 候选序号、本机路径、`skip` |
| `plan-` | 整份计划的总确认，`remove` 与 `stage` 才有 | `yes` / `no` |

退出码：0 完成，1 出错或被拒绝，2 命令行参数不对，3 还有问题等待回答。

## 时间戳

副本、建成的链接、暂存与还原搬运的文件和链接都写入记录里的修改时间，Windows 上还写入创建时间，NTFS 上精确到 100 纳秒。

Windows 上 `os.utime` 的 `follow_symlinks=False` 抛 `NotImplementedError`，链接自身的修改时间没有其他 Python 接口能写，所以 `fs.set_times` 用 `SetFileInformationByHandle`：以 `FILE_FLAG_OPEN_REPARSE_POINT` 打开链接本身，一次写入 `CreationTime` 与 `LastWriteTime`，不碰链接指向的目标。

Windows 之外的平台没有写创建时间的接口，创建时间停在重建的那一刻，修改时间对文件和链接都能写。硬链接与源共享 inode，两个时间都随源，无法单独设置。

设置时间失败只输出警告，路径的内容与指向已经就位。

## 平台差异

Windows 上 `os.rename`、`os.replace`、`shutil.move` 作用在链接的目标上，链接本身的移动一律是「读指向，在新位置重建，再删旧的」。

`fix` 换链接同样走这条路，删除与新建之间中断会让该路径消失。路径不存在就不在 `fix` 的扫描范围内，重跑 `fix` 不会处理它。所以 `fix` 在删掉每条失效链接之前往 `state.jsonl` 追加一行，记下路径、新指向与 mtime，成功收尾时这行随日志一起丢弃。中断后剩下的行标出了当时处理到哪一条：最后一行是当时正在处理的那条，按行里的指向与时间手工建一条链接即可。

Windows 记录链接自身指向文件还是目录（`st_file_attributes` 的 `FILE_ATTRIBUTE_DIRECTORY` 位），所以失效链接也能正确重建。POSIX 不记录也不需要，`os.symlink` 没有类型参数。

`os.readlink` 在 Windows 上返回带 `\\?\` 前缀的绝对路径，读到的指向先去掉前缀再判断绝对与相对，否则 `isabs` 会把它判成相对路径。

junction 按目录链接处理，重建时变成目录符号链接，转换时打一行警告。`os.path.islink` 认不出 junction，扫描时用 `os.path.isjunction` 一并识别，否则递归会进入 junction。

## 参数

| 命令 | `--state` | `--base` | `--scan` | `--staging` | `--prefer` / `--pick` | `--rel-mode` |
| --- | --- | --- | --- | --- | --- | --- |
| `remove` | 可选 | 可选 | 必给 | — | 是 | — |
| `stage` | 可选 | 可选 | 必给 | 必给 | 是 | — |
| `rebuild` | 必给 | 可选 | — | — | — | 是 |
| `restore` | 必给 | — | — | — | — | — |
| `fix` | 可选 | 可选 | 必给 | — | — | 是 |
| `status` | — | — | — | — | — | — |

`status` 不取任何选项，只取一个位置参数：状态区或暂存区的容器目录，缺省时取当前工作目录。它按 `<容器>/.linktool/` 里存在哪份清单来判断这个目录是哪一种，不去别的目录找。

每个选项另有短名：`-b` 是 `--base`，`-x` 是 `--staging`（取自 eXchange），`-p` 是 `--prefer`，`-r` 是 `--rel-mode`。`-s` 与 `-S` 只差大小写，前者是 `--scan`，后者是 `--state`；两者收的都是目录路径，敲错大小写不会报错，路径会交给另一个参数。`--pick` 与 `--version` 没有短名。

四个选项各管一件事：

- `--state` 是记录所在的目录，记录写在 `<state>/.linktool/`。缺省时取唯一的 `--scan` 路径，并在日志里说明记录落在哪里；给出多个扫描路径又没有 `--state` 时报错。
- `--base` 决定记录的路径相对谁写、哪些链接写成相对。缺省时等于 `--state`。把它设成 `--state` 的上级，两棵并列的树之间也能用相对路径。
- `--scan` 是不设默认值的扫描路径，`remove`、`stage`、`fix` 至少给一个。
- `--staging` 是暂存区目录，`stage` 至少给一个。成员优先放进与它同卷的那个暂存区，没有同卷的就用第一个；只有真正放进条目的暂存区才写进记录。暂存区由工具建立：`stage` 在第一轮就建出给出的目录，答 `no` 时留在磁盘上的是一个空目录。

`--scan`、`--prefer`、`--staging` 一次可以带多个值（`--scan A B`），也可以重复出现（`--scan A --scan B`），两种写法结果相同。`--rel-mode` 取 `base`（只把基准目录内的链接转相对）、`all`（全部尝试）或 `off`（保留绝对），默认 `base`。`--pick` 默认 `ask`。

参数里的相对路径按当前工作目录补全；`~` 由 shell 展开，带引号时它就是一个名为 `~` 的目录名。计划文件的 `args` 段存的是补全后的绝对路径，因此同一个计划与从哪个目录敲命令无关。
